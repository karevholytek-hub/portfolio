# Правила оценки каждой итерации

**Три независимых уровня:**

- Технический preflight на каждом PR/push: проверка манифеста, unit tests защиты от ложного PASS, Chromium 390/768/1440, консоль, responsive, работоспособность навигации, валидность локальных ресурсов.
- Обязательная визуальная оценка: исходные фото Мышки vs текущие кадры, анатомия, шерсть, контакт лапы и головы, отсутствие эффекта резины, 10-секундный реальный видеозахват при 1×, минимум 12 кадров в контакт-листе, четыре цели курсора и touch.
- Выпуск: все G01–G08 = PASS с файлами доказательств и SHA256, итоговый HTML с совпадающей контрольной суммой, реальный Telegram URL; запуск python qa/check_release.py --mode release.

**Нельзя** превращать изменение вершин/пикселей в утверждение, что движение естественное. Нельзя использовать «не проверено на реальном телефоне» как PASS. Провал одного критического блока отвергает всю сборку. Если человек на своём устройстве видит статичную кошку, возвращаем G06 в FAIL.

Рекомендуемые показатели производительности: минимум 30 FPS на реально измеренном целевом устройстве, 50–60 FPS желаемо; точных цифр нельзя обещать без замеров. Без WebGL — качественный резервный режим, без обманного «живая кошка» из нескольких кадров.

Пока qa/release.json имеет release_ready=false: проект **BLOCKED**, даже если технический CI стал зелёным. Для блокирования прямого push в main нужно включить required status checks/branch protection в настройках GitHub; workflow сам по себе этого не обеспечивает.
